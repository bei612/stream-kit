# Android managed client integration

Status: implementation in progress, not an APK delivery claim. Scope: [current goal](../docs/goal-current.md).

## One managed session and transport

The Android fork lives in `third_party/moonlight-android`, pinned to official v12.2 with recursive source dependencies recorded in `third_party-manifests/moonlight-android.json`. All files are ordinary Git files; `.gitmodules` declarations are retained as manifest text only. Upstream OpenSSL/Opus static archives are present in the imported snapshot; this is not evidence that those libraries were rebuilt here. Their production dependency provenance must be addressed in Android packaging.

Upstream `NvConnection` directly creates a GameStream connection and cannot be used as the platform admission path. Managed Android playback will use the existing gateway's WebRTC endpoint and shared upstream. The gateway already rejects legacy WebSocket streaming in managed mode; that restriction remains. No new Android-only renderer, bypass pairing endpoint, or second upstream is added.

Reuse the official Android native platform and gesture implementation through transport interfaces. `PointerInput` decouples the existing absolute/relative touch recognizers from `NvConnection`; `ManagedInput` adapts them and upstream `KeyboardTranslator` to the existing gateway input packets. Pressed keys are released on loss of window focus or stop. The pinned native WebRTC library handles peer negotiation, secure RTP and audio capture/playout. No WebView streaming wrapper is used.

## Admission and authority

1. Parse the same `/watch#key=...` capability used by Web. Send it only as a Bearer header to `/api/v1/watch/open`; never log it, include it in HTTP query strings or send administrator credentials.
2. Redeem the returned short-lived invitation with `/api/v1/client-sessions/join`. Check application identity; retain the connection credential for heartbeat, ticket, resume and leave operations.
3. Consume the existing revision/control-epoch snapshot, 5-second heartbeat and 15-second lease policy described in [connection lifecycle](client-connections/README.md). Media tickets authorize media admission; their role field does not overwrite heartbeat authority.
4. Join the gateway using native WebRTC with its existing SDP extensions, media-ticket authentication and `moonlight.control` data channel. Program audio and authorized microphone use the existing shared mixer and target routing.
5. Both server-side guards and native input/microphone gates apply. Revoke input and release physical recording on permission denial, authority loss, disconnect, background transition or stop. Ignore stale revisions and callbacks belonging to an interrupted session attempt. A resumed viewer never inherits controller authority.

`WatchLink`, `ConnectionAuthority` and `AuthorityState` implement the pure-Java authority boundary. `ManagedApi` now implements the admission, heartbeat, resume, ticket, leave and WHEP HTTP adapter with isolated credentials, disabled redirects, bounded responses and same-gateway resource checks. `NativePeer` implements native WebRTC receive tracks, a microphone sender and a gated control data channel, reusing upstream `StreamConfiguration`. It disables both physical recording and the sending track on microphone stop. The native library and notices are pinned in `third_party-manifests/android-media.json`.

`ManagedSession` owns asynchronous admission, heartbeat, authority expiry, reconnect and late-result cleanup. `ManagedActivity` presents native video, permission controls and the upstream absolute-touch recognizer. Backgrounding leaves the connection and releases capture; returning rejoins as a viewer. Audio-focus loss disables capture and playout. Microphone capture requires an explicit user action, Android permission and current controller authority. Returning to foreground or reconnecting does not automatically restore recording consent. First-frame visibility is tracked per peer so a reused renderer cannot leave the link editor visible after reconnect.

## Configuration and product boundary

Use a distinct Stream Kit application ID, durable release signing key and version code for upgrades. Release TLS validates certificates and hostnames; private LAN CA trust needs explicit provision. Any development HTTP access is restricted to an explicit debug policy. No fake audio, Example, probing components, SDK tools or signing secrets are packaged with the production App.

The product identity is `io.github.bei612.streamkit` (debug has a separate `.debug` ID). The persistent project certificate fingerprint is in `third_party-manifests/android-signing.json`; the private PKCS12 key and its Windows DPAPI-protected password are kept outside the repository, with a copy in repository Actions secrets for signing. Do not regenerate this identity for upgrades. Local builds use `scripts/android/build-release.ps1 -Version ... -VersionCode ...`; `android-release-candidate` creates signed artifacts on demand and does not publish them as production. Packaging checks enforce the certificate, version, non-debuggable identity, embedded clean source revision, pinned WebRTC notices and exclusion of test dependencies. Resolved runtime hashes and native-library hashes accompany the candidate. This inventory does not claim that upstream static archives were locally rebuilt.

Android and Web join with bounded `client_type` metadata; the management page labels their connections. Missing metadata remains `unknown` for compatibility. This client-reported label never grants authority and survives connection persistence/resume. No separate account or session registry is introduced.

One bookmark is encrypted using Android Keystore AES-GCM in the application's no-backup directory. Storage runs off the UI thread. The editor clears the capability after connecting and displays only the origin; process relaunch loads the bookmark but waits for a connect gesture. Users can clear the saved link. Android versions before API 23 or unavailable keys retain only an in-memory link with an explicit notice; no plaintext persistence fallback exists. Key invalidation/ciphertext authentication failure requires re-entry. This follows the [Android Keystore guidance](https://developer.android.com/privacy-and-security/keystore); hardware-backed key storage is not assumed on every device.

Address changes must resolve to a verified server identity before sending stored capabilities; numeric-IP bookmarks do not rewrite themselves. The existing pending LAN TLS/IP-change delivery items remain open.

## Verification

`JAVA_HOME=... node scripts/test-android-protocol.mjs` checks link credential isolation, viewer denial, permission denial, revision/epoch ordering, revocation, consent and stale callback suppression with JDK 17+. These are protocol unit checks, not Android integration acceptance.

`./gradlew :app:testNonRootDebugUnitTest :app:assembleNonRootDebug` compiles the native client and exercises the HTTP adapter using OkHttp MockWebServer in test scope only. Eleven JVM tests cover credential isolation, redirects, mismatched-identity cleanup, media-resource isolation, authority decoding, ICE quoting and input wire packets. Valid upstream `StreamConfiguration` construction loads Android JNI and is exercised on the emulator, not in the Windows JVM.

The local official Android 16 x86_64 AVD `StreamKit_API_36` runs with WHPX. A native debug APK opened the existing Example permanent link, started the application and displayed actual decoded frames. A confirmed HOME/background/foreground transition returned to viewing with microphone disabled and the link entry hidden on the new peer's first frame. See `docs/evidence/android-native-viewer-20261106.json`. A later bookmark build survived force-stop/relaunch and connected again through its saved encrypted entry. This used debug HTTP through the emulator host alias; it does not prove release TLS, audio, controller input or physical-device behavior. Mixed Android/Web control transfer and audio, and a published download remain required. No repeated user speech session is imposed.

The first signed CI candidate exposed an R8/JNI failure absent from Debug. The pinned AAR omits consumer rules, so the application now retains the WebRTC Java ABI and JNI Zero's annotated native entry points while keeping app/resource optimization enabled. The corrected signed release displayed actual Example video through normal HTTPS verification after installing an isolated CA in the emulator's user store. The loopback-only TLS fixture is a test helper and does not modify host trust or installed services; it does not close the production LAN TLS requirement. A separate `src/androidTest` instrumentation APK checks native initialization and audio codec capabilities against the minified release; it does not record audio and is excluded from the download package. Build locally with `-IncludeNativeSmoke`, then use `adb shell am instrument -w io.github.bei612.streamkit.test/com.limelight.streamkit.NativeLibrarySmoke`. The candidate workflow runs the same gate on an official emulator. Evidence and the original failure are retained in `docs/evidence/android-release-tls-20261106.json`.

CI run `42175104280` passed that gate and produced signed version `0.1.0-preview.20261106.2` (source `170fb688`). The downloaded APK was installed and displayed Example video over verified HTTPS on the local emulator. This is a usable native viewer candidate, not completed controller/microphone acceptance or a published production release.

## Local emulator operation

`scripts/android/start-emulator.ps1` reuses the installed official SDK and the `StreamKit_API_36` AVD, refusing an occupied or mismatched device port. By default it runs headlessly; pass `-ShowWindow` when starting a new instance for interactive debugging. An already running instance is reused without restart. It does not download additional images, wipe device data, enable gRPC, modify host virtualization or alter the installed Stream Kit services. ADB serial is `emulator-5580`; boot readiness is `adb -s emulator-5580 shell getprop sys.boot_completed` returning `1`.

The Windows emulator's experimental gRPC microphone control/injection stalled the isolated AVD during automated audio preparation. It was removed from the running configuration and no microphone pass is claimed. The standard AVD was restored and the CI APK's actual native viewing was verified afterwards. Do not ship emulator tools, synthetic sources or instrumentation APKs with the product.
