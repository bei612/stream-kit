# Stream-Kit Orchestrator 需求文档

## 2026-10-30 当前交付约束与新增核心验收

以下要求优先于本文较早版本：平台保留一个管理员；Web 客户端跨平台，服务器支持原生 Windows 和 Linux。本轮不要求 Linux 与手机真机验收，但代码兼容和自动化检查保留。

- 桌面采集与指定程序采集必须可配置。程序模式统一绑定目标程序的画面、声音、输入控制与麦克风接收；启动指定程序后采集整个桌面不算完成程序模式。需要验证覆盖窗口、切换前台、程序退出等情况下不会回退泄露桌面/其他应用声音。
- example 扩展为综合功能验证程序，覆盖麦克风设备选择、实际接收电平、录音/回放、程序主动播放声音、画面变化和控制输入。验收基于程序实际采集与输出，不能用浏览器授权成功替代目标程序录音成功。
- 应用入口同时支持上传压缩包和指定本机已经存在的程序路径。支持 ZIP、7z 及其他常用压缩格式；统一处理解压安全、空间限制、失败清理与入口检测。本机路径应用不得套用上传包的目录所有权规则误删原程序。
- 全部受支持的可配置参数纳入统一管理页，按所属组件和用途组织；参数明确标注即时生效、重连生效或重启生效，并区分已保存的期望值与实际生效值。不能仅展示脱敏配置 JSON 代替配置功能。
- 所纳管开源组件均进行必要二开，通过统一数据模型、协议、生命周期和管理入口整合；保持管理端、观看端专业一致的轻量视觉设计，不新增重型监控、多用户体系或非核心装饰性服务。
- 开发持续进行，阶段性复核、提交并推送；仅以实际源码、构建、运行与验收证据判断完成度。

example 已增加原生音频设备选择、电平、限时录音/回放和测试音，代码与窗口生命周期检查通过，真实目标录音仍需验收。上传已支持 ZIP、7z、RAR、TAR 及 gzip/bzip2/xz/zstd 压缩的 TAR，包含实际解码与 HTTP 上传清理测试。本机程序路径注册已纳入统一管理页，使用现有单管理员与应用生命周期。指定程序独立画面/声音采集及完整参数编辑仍需实现或逐项补齐，不因要求已写入文档而计为完成。

本机程序由 `source=local` 明确标记；旧上传记录迁移为 `source=archive`。两者的 `app_dir` 始终是平台存储中的 UUID 子目录，用于所属日志/图标；本机 `exe_path/working_dir` 是外部引用，删除仅清理平台注册目录，不能把外部程序目录作为删除目标。注册要求绝对路径、有效程序类型和工作目录，Linux 要求执行位；不自动启动程序。管理页展示来源与完整入口，移除本机注册时说明原文件保留。`{app_dir}` 启动参数占位符对本机来源表示程序所在目录，路径中的空格和 Sunshine 环境变量转义由统一命令构建处理。注册保存与 Sunshine 注册状态沿用现有状态机；失败可重试。

压缩包解码在控制面内使用锁定且已纳入 `orchestrator/vendor` 的 Go 源码，不依赖系统安装 7z/WinRAR 命令。所有格式共用 `os.Root` 目录约束、类型检查、写入前大小预算、条目数量限制与重复路径检查；数量包含隐式创建的目录，保留 Linux 可执行位但去除特权权限。上传接收限制在解析 multipart 前生效；完整压缩后缀保留，临时上传包在成功和失败路径均清理。加密包、分卷包、链接/特殊文件明确不作为应用包支持范围。RAR/xz/zstd 解码字典/窗口另有限制；7z 头部和解码器内存的完整上限与异常包压力仍需生产加固，不能将磁盘写入限制宣称为全进程内存隔离。

> ⓪ Orchestrator 是整个 stream-kit 的**统一管理中心**，负责：
> 1. 管理所有串流组件（① Sunshine、② web-server、③ streamer）的启停和监控
> 2. UE5 应用包的上传、解压、注册、生命周期管理
> 3. 提供统一的 Web 管理界面

## 1. 项目背景与目标

### 1.1 背景

当前 stream-kit 项目包含三个子系统，需要分别手动启动和管理：

| 编号 | 程序 | 角色 | 当前问题 |
|------|------|------|---------|
| ① | Sunshine | 串流服务端，屏幕捕获 + 编码 + 推流 | 需手动安装启动，无统一管控 |
| ② | web-server.exe | Web 中转服务器 | 需手动启动，与 ① 独立运行 |
| ③ | streamer.exe | 串流子进程（由 ② 管理） | 由 ② 自动管理，但 ⓪ 需要感知其状态 |

用户需要一个**统一控制面板**来管理所有组件，并支持上传 UE5 应用包、一键推流。

### 1.2 目标

开发 ⓪ Orchestrator 独立服务，实现：

1. **统一进程管理**：⓪ 作为主控程序，管理 ①②③ 所有组件的启动、停止、重启和监控
2. **应用包管理**：上传 UE5 压缩包 → 自动解压 → 自动注册到 Sunshine → 浏览器即可串流
3. **UE5 进程管理**：对上传的 UE5 应用进程的全生命周期管理
4. **统一 Web 界面**：一个界面管理一切，包含组件状态、应用管理、串流入口

### 1.3 目标用户

**外部客户**（非技术人员），要求：
- 操作界面必须傻瓜式，不依赖命令行
- 错误提示使用友好中文，附带操作建议（如"Sunshine 未运行，请检查是否已安装"）
- 首次使用提供引导式配置（向导 / 引导页）
- 不暴露技术术语（PID、CSRF、PE 头等仅在日志中出现，不在 UI 中展示）

### 1.4 关键业务约束

- **同一时间仅 1 个串流**：Sunshine 单实例，同时只能串流一个 UE5 应用
- **仅通过串流启动 UE5**：用户在浏览器点击串流 → Sunshine 自动启动 UE5 exe → 画面推送到浏览器。⓪ 不需要直接启动 UE5 进程
- **应用包 20GB+**：典型 UE5 打包产物很大，上传需支持断点续传

### 1.5 设计原则

- **⓪ 是唯一需要手动启动的程序**：⓪ 负责拉起和管理 ① ②
- **不侵入**：不修改 Sunshine、Moonlight-Web-Stream 的源码，通过进程管理 + HTTP API 集成
- **风险隔离**：组件进程独立，单个崩溃不影响其他组件
- **质量可控**：独立测试、独立部署、独立版本管理
- **对客户友好**：UI 简洁直观，操作结果即时反馈，出错有明确中文提示

## 3. 技术栈

### 3.1 后端

| 层 | 技术 | 说明 |
|----|------|------|
| 语言 | **Go 1.22+** | 单二进制编译，无运行时依赖，Windows 原生支持 |
| HTTP 框架 | **Gin** | 生态最大，中间件丰富 |
| 数据库 | **SQLite** (via `modernc.org/sqlite`) | 纯 Go 实现，无 CGO 依赖，单文件存储 |
| ORM | **GORM** | 与 SQLite 配合，模型驱动 |
| 进程管理 | `os/exec` + `golang.org/x/sys/windows` | Windows API 直接调用（不用 `syscall`） |
| 文件锁 | `github.com/gofrs/flock` | Go 原生无 Windows 文件排他锁，需要此库 |
| 解压 | `archive/zip`、`archive/tar`、`github.com/bodgit/sevenzip` | 原生支持 zip/tar/7z |
| WebSocket | `github.com/coder/websocket` | gorilla/websocket 已归档，此库活跃维护且支持 context |
| 日志 | `go.uber.org/zap` + `lumberjack` | 结构化日志 + 轮转 |
| 配置 | `github.com/spf13/viper` | 支持 JSON/TOML/YAML + 环境变量 |
| 文件上传 | `multipart/form-data` + `io.Copy` 流式写入 | v1.0 使用标准 multipart；tus 断点续传列入 v2.0 |
| HTTP 客户端 | `net/http` | 调用 Sunshine API |
| 定时任务 | `time.Ticker` / goroutine | 进程健康检查轮询 |

### 3.2 前端

| 层 | 技术 | 说明 |
|----|------|------|
| 框架 | **Vite 8 + React Router 7** | 纯 CSR SPA，无 SSR 限制，构建快，动态路由无障碍 |
| 语言 | **TypeScript** | 类型安全 |
| UI 组件库 | **shadcn/ui** + **Tailwind CSS** | 现代化 UI，可定制 |
| 服务端状态 | **TanStack Query (React Query)** | API 数据缓存、自动刷新 |
| 客户端状态 | **Zustand** | WebSocket 连接状态、上传进度、UI 状态 |
| 实时通信 | **WebSocket** (原生) | 接收 ⓪ 推送的组件状态和进度 |
| 图标 | **Lucide React** | 统一图标风格 |
| 文件上传 | **XMLHttpRequest** (`upload.onprogress` + `abort`) | v1.0 标准上传（含进度+取消）；tus 断点续传列入 v2.0 |
| 构建输出 | `vite build` → `dist/` | 纯静态文件，由 Go 后端 serve |

### 3.3 前后端集成

```
开发模式：
  Vite dev server (:5173) → 代理 /api/* 请求到 Go 后端 (:9000)

生产模式：
  vite build → 输出到 dist/ 目录
  Go 后端 serve dist/ + 提供 /api/* 路由
  用户只访问 Go 后端的 :9000 端口
```

**SPA 路由回退**：Go 后端对非 `/api/*` 且非静态文件的请求一律返回 `index.html`，由前端 React Router 处理路由。

### 3.4 SQLite 关键配置

```go
// 必须限制为单连接，避免 "database is locked" 错误
db.SetMaxOpenConns(1)
// 启用 WAL 模式提升并发读性能
db.Exec("PRAGMA journal_mode=WAL")
db.Exec("PRAGMA busy_timeout=5000")
```

### 3.5 Go 工程约束

- 所有长期运行的 goroutine 必须有 `defer recover()` + 错误日志，panic 不得杀死 ⓪ 进程
- 所有 goroutine 通过 `context.Context` 管理生命周期，⓪ 收到 `os.Interrupt` 时通过 root context 取消
- Windows 专用代码使用 `//go:build windows` 标签隔离，Linux 提供空实现
- 构建命令：`CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build`

## 4. 术语定义

| 术语 | 定义 |
|------|------|
| **组件** | ① Sunshine、② web-server.exe、③ streamer.exe 三个串流子系统的统称 |
| **应用包** | 用户打包的 UE5 应用压缩文件（zip/tar/tgz/7z） |
| **应用** | 解压后在系统中注册的一个可运行 UE5 程序 |

| **启动参数** | 传递给入口 exe 的命令行参数 |

| **Sunshine 注册** | 通过 ① HTTP API 将应用添加到其应用列表 |

#### FR-5.1.2 进程启动

- ⓪ 启动时根据 `auto_start` 配置决定是否自动拉起各组件
- 启动顺序：① Sunshine → ② web-server.exe（等 ① 健康检查通过后再启动 ②，可配置）
- 通过 `os/exec.Command` 启动子进程，捕获 stdout/stderr
- 记录每个组件的 PID

#### FR-5.1.3 进程停止

- ⓪ 提供 API 停止单个组件
- **子进程启动参数**（Windows）：

  ```go
  cmd.SysProcAttr = &syscall.SysProcAttr{
      CreationFlags: windows.CREATE_NEW_PROCESS_GROUP, // 独立进程组，用于定向发送 CTRL_BREAK
      HideWindow:    true,                              // 隐藏控制台窗口
  }
  ```

- **停止策略**（Windows）：
  - 控制台程序（① ②）：`GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, childPID)` 发送优雅关闭 → 超时后 `TerminateProcess`
    - 注意：`CTRL_C_EVENT` 在 `CREATE_NEW_PROCESS_GROUP` 下被禁用，只能用 `CTRL_BREAK_EVENT`
  - GUI 程序（UE5）：通过 `EnumWindows` + `GetWindowThreadProcessId` 找到目标 PID 的所有窗口句柄 → 对每个 HWND 发送 `PostMessage(WM_CLOSE)` → 超时后 `TerminateProcess`
  - **子进程判断**：读取 exe 的 PE 头 `IMAGE_OPTIONAL_HEADER.Subsystem` 字段（2=GUI, 3=Console）选择停止策略
  - `TerminateProcess` 只终止目标进程本身，**不终止其子进程**（Windows 限制）。已知可能残留的子进程：CrashReportClient.exe 等，接受此限制
- 停止 ② 时 ③ 会自动退出（kill_on_drop）
- **⓪ 自身退出**：`SetConsoleCtrlHandler` 捕获 `CTRL_C_EVENT` / `CTRL_CLOSE_EVENT` / `CTRL_SHUTDOWN_EVENT`
  - `CTRL_CLOSE_EVENT` 有 OS 强制的 **~5 秒期限**，期限内必须完成清理
  - 因此优雅关闭超时设为 **5 秒**（非 30 秒），逆序停止：UE5 → ② → ①
  - 如果 5 秒内未完成，OS 会强制终止 ⓪（子进程成为孤儿，下次启动时通过 PID 文件接管）
- **区分主动停止与崩溃**：⓪ 在发送停止信号前设置 `stopping` 原子标志，`cmd.Wait()` goroutine 检查此标志
- **文件句柄释放**：`TerminateProcess` 后需等待进程句柄关闭（`cmd.Wait()` 返回），再等 **1 秒**（Windows Defender 可能短暂持有句柄），然后才能操作该进程的文件

#### FR-5.1.4 进程重启

- 提供单组件重启 API（stop + start）
- 提供全部重启 API

#### FR-5.1.5 崩溃自动恢复

- ⓪ 通过 goroutine 监控子进程退出事件（`cmd.Wait()`）
- 非预期退出（⓪ 未主动发送 stop）时：
  - 记录崩溃事件（退出码、时间、stderr 尾部）
  - 如 `restart_on_crash: true`，等待 `restart_delay_seconds` 后自动重启
  - 连续崩溃超过 `max_restart_attempts` 次后停止重试，标记为 `error`
  - 崩溃计数在成功运行超过 60 秒后重置

#### FR-5.1.6 健康检查

- 对 ① ② 进行周期性 HTTP 健康检查
- 检查逻辑：HTTP GET → 200 响应 = 健康
- 对 ③ streamer：通过查询 ② 的 WebSocket 连接状态间接感知（或通过进程列表检测）
- 健康状态：`starting` / `running` / `unhealthy` / `stopped` / `crashed` / `error`

#### FR-5.1.7 日志采集

- 捕获 ① ② 的 stdout 和 stderr 输出
- 存入内存环形缓冲区（最近 1000 行 / 每组件），通过 API 查询
- 可选：同时写入日志文件

#### FR-5.1.8 组件状态模型

```
                    auto_start
         ┌─────── STOPPED ◄────────── ⓪ 启动 / 用户 stop
         │            │
         │     ⓪ start / auto_start
         │            ▼
         │        STARTING ──────► 健康检查通过 ──► RUNNING
         │            │                                │
         │       启动失败                          进程退出
         │            ▼                                ▼
         │         ERROR              ┌──── CRASHED ◄──┘
         │                            │        │
         │                    restart_on_crash  │ 超过 max_restart
         │                            ▼        ▼
         │                        STARTING   ERROR
         └────────────────────────────────────────────────────
```

### 5.2 应用包上传

#### FR-5.2.1 文件上传

- 支持通过 Web 界面和 REST API 上传压缩包
- 支持的压缩格式：**zip、tar、tar.gz（tgz）、tar.bz2**（7z 列入 v2.0）
- **上传协议：HTTP multipart/form-data**（`POST /api/v1/apps/upload`）
  - 先存文件到临时目录，成功后再创建 DB 记录（防止孤儿数据）
  - 进度：前端通过 `XMLHttpRequest.upload.onprogress` 获取实时进度（字节级）
  - 取消：前端可调用 `xhr.abort()` 中止上传
  - 超时：30 分钟（适配大型 UE5 包）
- 上传表单字段：
  - `file`：压缩包文件（必填）
  - `name`：应用显示名称（必填，唯一）
  - `exe_path`：压缩包内的入口 exe 相对路径（可选，留空则自动检测）
  - `args`：启动参数（可选）
  - `args_template`：启动参数模板名称（可选，与 `args` 互斥）
- **v2.0 计划**：迁移到 tus 协议（分块断点续传），支持 20GB+ 文件中断恢复

#### FR-5.2.2 上传约束

- 单文件大小上限：**默认 50 GB**，可配置（`max_upload_size_bytes`）
- 解压后总大小上限：**默认 50 GB**，可配置（`max_extract_size_bytes`）
- 允许的文件后缀白名单：`.zip`、`.tar`、`.tar.gz`、`.tgz`、`.tar.bz2`
- 同一时刻同一应用名仅允许一个上传任务（per-app TryLock 互斥）
- 上传进度通过 XHR onprogress 回调实时推送

#### FR-5.2.3 临时存储

- 压缩包先上传到临时目录（`temp/`）
- **`temp/` 和 `apps/` 必须在同一磁盘卷**上（`os.Rename` 跨卷会失败）。⓪ 启动时校验两者的盘符一致，不一致则报错提示
- 解压成功后删除临时压缩包
- 上传失败或解压失败时清理临时文件

### 5.3 自动解压

#### FR-5.3.1 解压流程

- 上传完成后立即自动触发解压
- 解压目标：`{托管目录}/{app_id}/`，每个应用完全隔离
- 解压完成后校验目录结构完整性

#### FR-5.3.2 安全校验

- **路径穿越防护**：解压前检查所有条目路径，拒绝包含 `..` 或绝对路径的条目
- **NTFS 保留名**：拒绝文件名为 `CON`、`PRN`、`AUX`、`NUL`、`COM1`~`COM9`、`LPT1`~`LPT9` 的条目（不区分大小写）
- **NTFS 特殊字符**：拒绝文件名包含 `:` 的条目（NTFS 交替数据流语法）；去除尾部空格和点号
- **MAX_PATH 防护**：解压时检查完整路径长度，超过 **240 字符**（留余量）的条目使用 `\\?\` 长路径前缀。部署文档建议启用 Windows 10 长路径策略（`HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled = 1`），因为 UE5 包目录结构常超过 260 字符
- **zip bomb 防护**：限制解压后总大小（默认 **50 GB**），超出则中止并清理
- **文件数量限制**：单个压缩包内文件数上限（默认 **100,000**），超出则拒绝
- **符号链接**：忽略压缩包内的符号链接
- **GBK 文件名**：zip 条目未设置 UTF-8 标志位（EFS, bit 11）时，尝试以 GBK 解码文件名（`golang.org/x/text/encoding/simplifiedchinese`）

#### FR-5.3.3 解压状态

- 解压过程通过 WebSocket 推送进度
- 失败时记录原因并清理已解压的部分文件

### 5.4 入口检测

#### FR-5.4.1 自动检测

当用户未指定 `exe_path` 时，⓪ 自动检测入口 exe：

1. 扫描解压根目录（及一级子目录）下的 `.exe` 文件
2. 排除已知非入口文件：`CrashReportClient.exe`、`UE4PrereqSetup_x64.exe`、`UnrealCEFSubProcess.exe` 及 `Engine/` 目录下的所有 exe
3. 如果只有**一个**候选 exe，自动选定
4. 如果有多个候选 exe，返回候选列表，要求用户通过 API/UI 选择

#### FR-5.4.2 手动指定

- 用户可在上传时通过 `exe_path` 字段指定入口 exe 的相对路径
- ⓪ 校验该文件是否存在且为 `.exe` 文件

#### FR-5.4.3 入口校验

- 检测 exe 文件是否为有效的 PE 格式（检查 MZ 头 `4D 5A`）
- 检测同级是否存在 UE5 特征（`Engine/` 目录或特征 DLL），作为 **警告**（不阻断）

### 5.5 Sunshine 应用注册

#### FR-5.5.1 自动注册

解压成功且入口 exe 确定后，⓪ 自动调用 ① Sunshine HTTP API 注册应用：

- API 端点：`POST https://localhost:47990/api/apps`
- 认证方式：HTTP Basic Auth（用户名密码从 ⓪ 配置读取）
- CSRF：从 `GET /api/csrf-token` 获取令牌，放入 `X-CSRF-Token` 头
- 注册内容：

```json
{
  "index": -1,
  "name": "应用显示名称",
  "cmd": "D:\\apps\\{app_id}\\MyGame.exe",
  "working-dir": "D:\\apps\\{app_id}\\",
  "output": "D:\\apps\\{app_id}\\output.log",
  "auto-detach": false,
  "wait-all": true,
  "exit-timeout": 10,
  "elevated": false,
  "prep-cmd": [],
  "detached": []
}
```

注意：启动参数（args）合并到 `cmd` 字段中，格式为 `exe路径 参数`。

#### FR-5.5.2 注册校验

- 注册前检查 ① 是否可达（`GET /api/apps`）
- 注册后重新查询应用列表确认注册成功
- 注册失败时记录错误，应用状态标记为 `register_failed`，支持手动重试

#### FR-5.5.3 注销

- 删除应用时，⓪ 同步从 Sunshine 中注销（`DELETE /api/apps/{index}`）
- 注销前需查询当前应用列表获取正确的 index（Sunshine 按名称排序，index 会变动）

### 5.7 UE5 应用进程管理

> UE5 应用**仅通过串流启动**：用户在 ② Moonlight-Web 界面点击应用 → Sunshine 自动启动 UE5 exe 并捕获画面。⓪ 不直接启动 UE5 进程。

#### FR-5.7.1 进程感知

- ⓪ 通过定期扫描进程列表（`CreateToolhelp32Snapshot` + exe 路径匹配）感知 Sunshine 启动的 UE5 进程
- 感知到后更新应用状态为 `running`，记录 PID
- 监控间隔：默认 **5 秒**，可配置

#### FR-5.7.2 进程停止

- ⓪ 提供 API 停止 UE5 应用（终止串流）：
  - 先调用 Sunshine `POST /api/apps/close` 终止串流会话（Sunshine 会负责关闭 UE5 进程）
  - 如果 Sunshine 不可达，⓪ 直接对 UE5 进程执行：`PostMessage(WM_CLOSE)` → 超时 → `TerminateProcess`
- 等待文件句柄释放后更新状态为 `stopped`

#### FR-5.7.3 崩溃检测

- ⓪ 定期检查已知 PID 是否存活
- 进程消失时：如果非 ⓪ 主动停止（检查 `stopping` 标志），记录为崩溃事件
- 记录：退出时间、output.log 尾部
- 标记应用状态为 `crashed`，**不自动重启**

#### FR-5.7.4 串流互斥

- Sunshine 同时只能串流一个应用
- 当用户在 ⓪ 界面点击"串流"按钮时，如果已有应用在串流中，先提示"将终止当前串流 XXX，是否继续？"
- 确认后调用 `POST /api/apps/close` 终止当前串流，再跳转到新串流

### 5.8 应用版本管理

#### FR-5.8.1 更新应用

- 用户可对已有应用上传新版本压缩包
- 更新流程：停止运行中的进程 → 备份旧版本目录（`{app_id}_bak_{timestamp}`）→ 解压新版本 → 更新 Sunshine 注册 → 删除备份
- 更新失败时自动回滚：恢复备份目录

#### FR-5.8.2 删除应用

- 删除流程：停止运行中的进程 → 等待文件句柄释放（1s）→ 从 Sunshine 注销 → 删除应用目录 → 删除数据库记录
- 目录删除失败（文件被锁）时重试 3 次，每次间隔 2 秒。仍失败则标记 `error`，留待人工处理
- API 需传 `confirm=true`

#### FR-5.8.3 磁盘管理

- 提供应用占用磁盘空间查询
- 可配置托管目录总容量上限
- 超出上限时拒绝新上传并提示

### 6.2 可靠性

| 指标 | 要求 |

## 9. 安全需求

### 9.1 文件上传安全

| 威胁 | 对策 |
|------|------|
| 路径穿越（Zip Slip） | 解压前校验所有条目路径，拒绝 `..` 和绝对路径 |
| Zip Bomb | 限制解压后总大小和文件数量 |
| 恶意 exe | 默认不提权（`elevated: false`） |
| 超大文件 DoS | 限制上传大小，`io.LimitReader` 流式写入 |

### 9.2 网络安全

| 威胁 | 对策 |
|------|------|
| JWT token 传输 | 默认绑定 `0.0.0.0:9000`；建议配置 TLS 或反向代理 |
| 未授权访问 | 用户名密码登录 + JWT 认证（`Authorization: Bearer <jwt>`）+ IP 登录限速（10 次/5 分钟） |
| 凭证泄露 | 配置文件中的密码不通过 API 返回；日志脱敏 |
| CORS | 仅允许同源请求（前端由同一端口 serve） |
| WebSocket 未认证 | 管理 JWT 握手头认证 + Origin 校验 + 到期关闭，不接受 URL 查询令牌 |

### 9.3 TLS 支持（可选）

- ⓪ 支持配置 TLS 证书直接提供 HTTPS 服务
- 配置字段：`server.tls_cert`、`server.tls_key`
- 不配置则为 HTTP（默认仅 localhost，安全）
- 远程访问推荐方式：配置 TLS 或使用反向代理（Nginx/Caddy）

### 9.4 进程安全

| 威胁 | 对策 |
|------|------|
| 进程提权 | 默认 `elevated: false` |
| 子进程泄漏 | ⓪ 优雅退出时逆序停止所有子进程；非正常退出由 OS 回收 |
| 资源耗尽 | 提供手动 kill 能力 |

### 9.5 威胁模型声明

⓪ 运行用户上传的 exe 文件，本质上是受控环境下的代码执行服务。**安全前提**：
- ⓪ 运行在受信任的内网环境中（非公网直接暴露）
- 上传者是受信任的用户（已通过用户名密码登录）
- UE5 应用来源可信（内部团队打包）

**v1.0 不做**的安全措施（过度设计）：
- 不做沙箱隔离（UE5 需要 GPU 直接访问，沙箱不可行）
- 不做代码签名校验（内部工具无此需求）
- 不做配置文件加密（文件系统权限已足够）

**建议部署措施**（文档提示，非代码实现）：
- 以普通用户运行 ⓪，不使用管理员权限
- 将 `apps/` 目录加入 Windows Defender 排除列表（避免误杀和性能问题）
- 配置 NTFS 权限限制配置文件仅当前用户可读

## 12. 约束与限制

### 12.1 技术约束

| 约束 | 说明 |
|------|------|
| Windows 平台 | UE5 打包产物为 Windows exe，⓪ 首要支持 Windows |
| Go CGO-free | 使用 `modernc.org/sqlite` 避免 CGO，简化交叉编译 |
| Next.js 静态导出 | 前端编译为纯静态文件，由 Go 后端 serve，不需要 Node.js 运行时 |
| Sunshine API | 应用列表按名称排序，index 不稳定，需实时查询 |
| Sunshine 单串流 | 同一时刻只能串流一个应用 |
| CSRF 令牌 | 有效期 1 小时，需缓存 + 过期重试 |

### 12.2 业务约束

| 约束 | 说明 |
|------|------|
| 应用名唯一 | ⓪ 和 Sunshine 中的应用名必须唯一 |
| 不自动重启崩溃的 UE5 进程 | 避免死循环；组件可自动重启，UE5 不自动重启 |
| ⓪ 不安装 Sunshine | 用户需自行安装 ①，⓪ 只管理其进程 |

### 12.3 不在范围内（v1.0）

| 内容 | 说明 |
|------|------|
| 多用户权限 | 初期单用户（config.json 配置用户名密码），不做多用户多角色 |
| 多工作站编排 | 初期单机部署 |
| 音视频转码 | 完全由 ①②③ 负责 |
| Sunshine 安装器 | 用户自行安装 |

## 14. 幂等性与并发控制

### 14.1 API 幂等性要求

所有写操作必须是幂等或安全的，防止网络重试和前端重复点击导致副作用：

| API | 幂等策略 |
|-----|---------|
| `POST /api/apps/upload` | 同一应用名在上传/解压期间拒绝重复提交（返回 `409 Conflict` + 当前任务状态） |
| `POST /api/apps/{id}/start` | 如果进程已在运行，直接返回成功 + 当前 PID（不重复启动） |
| `POST /api/apps/{id}/stop` | 如果进程已停止，直接返回成功（不报错） |
| `POST /api/components/{name}/start` | 如果组件已在运行，直接返回成功 |
| `POST /api/components/{name}/stop` | 如果组件已停止，直接返回成功 |
| `POST /api/components/{name}/restart` | 无论当前状态，执行完整 stop→start 流程 |
| `DELETE /api/apps/{id}` | 如果应用已删除，返回 `404`（不报 500） |
| `POST /api/apps/{id}/register` | 如果 Sunshine 中已存在同名应用，执行更新而非报错 |
| `PUT /api/apps/{id}` | 使用乐观锁（`updated_at` 字段），并发修改时后者返回 `409 Conflict` |

### 14.2 应用级操作互斥锁

每个应用维护一把内存互斥锁（`sync.Mutex`），以下操作互斥执行：

```
上传/解压 ←→ 启动 ←→ 停止 ←→ 更新 ←→ 删除
```

**规则**：
- 同一应用同时只能进行一个写操作
- 竞争时后到的请求返回 `409 Conflict`，附带当前正在进行的操作描述
- 读操作（GET 详情/状态/日志）不受锁限制
- 锁粒度为应用级，不同应用的操作互不阻塞

### 14.3 组件级操作互斥

每个组件维护操作互斥：
- 同一组件不能同时执行 start 和 stop
- restart 内部是 stop→start 原子序列，全程持锁
- 不同组件可并行操作

## 15. 事务一致性与故障恢复

### 15.1 多步骤流水线的一致性

#### 15.1.1 上传→解压→检测→注册 流水线

这是一个多步骤长事务，需保证每一步失败后系统状态干净：

```
步骤          成功后状态        失败时补偿动作
─────────────────────────────────────────────────────────
① 上传        uploading        删除 temp/ 中的临时文件
② 解压        extracting       删除 apps/{id}/ 目录
③ 检测入口    detecting        标记 error，保留文件（用户可手动指定 exe）
④ 注册 Sunshine registering    标记 register_failed，保留文件（用户可重试）
⑤ 完成        ready            —
```

**关键规则**：
- 每步开始前更新 DB 状态（先写状态再做操作）
- 每步失败时执行**补偿动作**清理已产生的副作用
- DB 状态更新和补偿动作在同一个 goroutine 内顺序执行，不依赖外部事务

#### 15.1.2 应用更新流水线

```
步骤          成功后状态        失败时补偿动作
─────────────────────────────────────────────────────────
① 停止进程    stopped          无（停止失败则中止更新）
② 备份旧目录  updating         恢复原目录名
③ 解压新版本  updating         删除新目录 + 恢复备份
④ 更新 Sunshine updating       删除新目录 + 恢复备份 + 重新注册旧版本
⑤ 删除备份    ready            保留备份（下次清理）
⑥ 完成        ready            —
```

#### 15.1.3 应用删除流水线

```
步骤          失败时行为
─────────────────────────────────────────────────────────
① 停止进程    失败则强制 kill，继续删除
② Sunshine 注销 失败记录警告，继续删除（可能 Sunshine 已不可达）
③ 删除目录    失败记录错误，标记 error（可能文件被锁定）
④ 删除 DB 记录 仅在 ③ 成功后执行
```

### 15.2 ⓪ 与 Sunshine 的数据一致性

#### 15.2.1 问题

用户可能通过 Sunshine 自身 Web UI（`https://localhost:47990`）直接增删应用，导致 ⓪ 数据库与 Sunshine 应用列表不一致。

#### 15.2.2 同步策略

- **启动时全量对账**：⓪ 启动时查询 Sunshine 应用列表，与本地 DB 比对：
  - DB 中有但 Sunshine 中无 → 尝试重新注册，失败则标记 `register_failed`
  - Sunshine 中有但 DB 中无 → 忽略（非 ⓪ 管理的应用）
- **操作前即时校验**：每次注册/注销前先查询 Sunshine 当前列表
- **不做实时双向同步**（复杂度过高，Sunshine 无 webhook），接受最终一致
- 提供手动"同步"按钮，触发全量对账

### 15.3 ⓪ 与文件系统的一致性

| 场景 | 处理 |
|------|------|
| DB 记录存在但 `apps/{id}/` 目录被手动删除 | ⓪ 启动时检测到，标记 `error`，提示"应用文件丢失" |
| `apps/{id}/` 目录存在但 DB 无记录 | ⓪ 启动时忽略（可能是手动放置的文件） |
| 解压中途 ⓪ 崩溃，留下不完整目录 | ⓪ 启动时检查状态为 `extracting` 的应用，清理其目录，重置为 `error` |
| 上传中途 ⓪ 崩溃，留下临时文件 | ⓪ 启动时清理 `temp/` 目录下所有文件 |

### 15.4 SQLite 事务策略

- 使用 **WAL 模式**（`PRAGMA journal_mode=WAL`）：允许并发读写
- 单个 API 请求内的多条 DB 操作使用**显式事务**（`db.Transaction(func(tx) error {...})`）
- 状态机流转必须在事务内完成（读旧状态 + 校验 + 写新状态）
- 避免在事务中执行 IO 操作（HTTP 调用、文件操作）：先 IO，再更新 DB

### 15.5 状态机合法转换

应用状态只允许以下转换，其余拒绝：

```
uploading    → extracting | error
extracting   → detecting | error
detecting    → registering | error | ready (需手动选 exe 时暂停在 detecting)
registering  → ready | register_failed
register_failed → registering (重试) | error
ready        → running | uploading (版本更新) | deleting
running      → stopped | crashed
stopped      → running | ready | uploading (版本更新) | deleting
crashed      → running (手动重启) | ready | uploading | deleting
error        → uploading (重新上传) | deleting
```

非法转换（如 `running` → `uploading`）必须先 stop 再操作。

## 16. 边界条件与容错

### 16.1 ⓪ 自身生命周期

#### 16.1.1 单实例保护

- ⓪ 启动时在数据目录创建 `orchestrator.lock`，使用 `github.com/gofrs/flock` 获取排他锁（Go 原生 `os.OpenFile` 不支持 Windows 排他锁）
- 锁文件写入当前 PID
- 第二个实例启动时获取锁失败 → 读取 PID 检查是否存活 → 存活则报错退出，不存活则强制接管

#### 16.1.2 Windows 信号处理

- 使用 `os/signal.Notify(c, os.Interrupt)` 捕获 Ctrl+C
- Go 在 Windows 上的 `os.Interrupt` 同时覆盖 `CTRL_C_EVENT`、`CTRL_CLOSE_EVENT`、`CTRL_LOGOFF_EVENT`、`CTRL_SHUTDOWN_EVENT`
- **不使用 `syscall.SIGTERM`**：Windows 上无实际效果，外部 `taskkill` 直接调用 `TerminateProcess` 不触发信号
- `CTRL_CLOSE_EVENT`（用户关闭控制台窗口）有 OS 强制的 **~5 秒期限**，超时后 OS 直接杀进程
- 因此 ⓪ 的优雅关闭超时统一设为 **5 秒**

#### 16.1.3 子进程清理策略

> **设计决策**：不使用 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，因为它与⓪ 升级后接管旧进程矛盾。

**正常退出**：⓪ 通过 `SetConsoleCtrlHandler` 捕获关闭信号 → 逆序优雅停止所有子进程 → 退出。

**异常崩溃**（⓪ 被 kill 或 panic 导致未执行 shutdown）：
- 子进程（① ② UE5）会继续运行（成为孤儿进程）
- 新 ⓪ 启动时通过 PID 文件 + 进程名/路径匹配检测这些进程，重新接管
- 接管：将已有 PID 记录到管理器中，恢复监控
- 不匹配（PID 已被其他进程复用）：忽略，按全新启动处理

**实现**：⓪ 将所有子进程的 PID 持久化到 `data/pids.json`，格式：
```json
{"sunshine": 1234, "web_server": 5678, "apps": {"app-uuid": 9012}}
```

#### 16.1.4 ⓪ 自身升级

- 升级步骤：Ctrl+C 停止 ⓪（优雅关闭所有子进程）→ 替换 exe → 启动新 ⓪（`auto_start` 重新拉起组件）
- 如需保持子进程不中断：手动 `taskkill /F` 杀 ⓪（子进程存活）→ 替换 exe → 启动新 ⓪（通过 PID 文件接管）
- 不支持热更新（v1.0 范围内）

### 16.2 启动阶段边界条件

| 场景 | 处理 |
|------|------|
| config.json 不存在 | 生成默认配置（admin/admin），暂停提示用户检查配置后重启 |
| config.json 格式错误 | 启动失败，输出具体 JSON 解析错误行号 |
| `exe_path` 指向不存在的文件 | 启动时 warn 日志，组件标记为 `stopped`（不阻止 ⓪ 启动） |
| 端口 9000 被占用 | 启动失败，明确提示 `port 9000 already in use`，建议更换或检查是否重复启动 |
| ① 端口 47989/47990 被占用 | ① 启动失败，⓪ 记录错误，按崩溃重试逻辑处理 |
| ② 端口 8080 被占用 | 同上 |
| SQLite 数据库文件损坏 | 启动失败，提示备份并删除 db 文件重建 |
| `apps/` 目录不存在 | 自动创建 |
| `temp/` 目录不存在 | 自动创建 |
| 磁盘空间不足 | 启动时检测，warn 日志提示 |

### 16.3 组件启动边界条件

| 场景 | 处理 |
|------|------|
| ① 启动后健康检查一直不通过 | 启动超时（默认 **60 秒**，可配置 `startup_timeout_seconds`），超时后标记 `error` |
| ① 启动成功但 3 秒内退出 | 视为启动失败（非崩溃），标记 `error` |
| ② 依赖 ① 但 ① 处于 error | ② 仍可启动（可能连不上 Sunshine，但 web UI 可用），⓪ 发出 warn |
| 组件配置中 `auto_start: false` | ⓪ 不自动拉起，用户需手动启动 |
| 组件配置中 `restart_on_crash: false` | 崩溃后不自动重启，仅记录事件 |

### 16.4 上传与解压边界条件

| 场景 | 处理 |
|------|------|
| 上传到一半网络断开 | 不完整临时文件在请求超时后由清理 goroutine 删除（5 分钟无写入） |
| 压缩包解压后是空目录 | 标记 `error`，提示"压缩包内无有效文件" |
| 压缩包内所有 exe 都在排除列表中 | 标记 `detecting`，返回空候选列表，提示用户手动指定 |
| 解压目录已存在（上次残留） | 先删除旧目录再解压（已通过互斥锁保证不会与运行中冲突） |
| 解压过程磁盘空间耗尽 | 捕获写入错误，执行补偿清理，标记 `error` |
| 压缩包内文件名含非 ASCII 字符 | zip 使用 Go 标准库自动处理 UTF-8；GBK 编码的 zip（Windows 中文环境常见）尝试 GBK 解码回退 |
| 7z 格式含密码保护 | 返回错误"不支持加密压缩包" |

### 16.5 进程管理边界条件

| 场景 | 处理 |
|------|------|
| Sunshine 从外部启动了 UE5 应用（用户通过 ② 点击串流） | ⓪ 通过定期扫描进程名 + 匹配 exe 路径发现，更新 PID 和状态为 `running` |
| UE5 进程被外部 kill（如任务管理器） | ⓪ 下次轮询时检测到 PID 不存在，标记 `stopped`（退出码未知标记为 `crashed`） |
| 多个同名 exe 同时运行 | ⓪ 只跟踪自己启动的 PID，不匹配其他同名进程 |
| WM_CLOSE 发送后进程无响应 | 等待 `graceful_shutdown_timeout_seconds` 后 `TerminateProcess` 强制终止 |
| TerminateProcess 也失败（极罕见） | 记录错误，PID 标记为 orphan，用户需手动处理 |
| ⓪ 重启后发现旧 PID 仍在运行 | 通过 PID + exe 路径双重校验确认身份，匹配则接管，不匹配则忽略 |

### 16.6 Sunshine API 边界条件

| 场景 | 处理 |
|------|------|
| Sunshine 未运行 | API 调用超时，操作标记失败，不阻塞其他功能 |
| Sunshine 认证失败（401） | 记录错误 `auth_failed`，提示检查配置中的用户名密码 |
| CSRF token 过期 | 捕获 403，自动重新获取 token，重试一次 |
| Sunshine 应用列表中已有同名应用（非 ⓪ 注册） | 跳过注册，记录 warn，⓪ 标记 `register_failed` + 提示名称冲突 |
| 注销时 Sunshine 中找不到对应应用（已被手动删除） | 视为成功（目标状态已达成），继续删除流程 |
| Sunshine API 返回格式变化（版本不兼容） | 记录完整响应体到错误日志，标记失败 |
| 网络抖动导致注册成功但响应丢失 | 重试时先查询列表确认是否已存在，存在则视为成功 |

## 17. 运维与可观测性

### 17.1 日志管理

本系统有 **4 类日志**，各有不同用途、格式和保留策略：

#### 17.1.1 ⓪ 应用日志（Application Log）

**用途**：记录 ⓪ 自身的运行状态、请求处理、错误信息。

| 属性 | 规格 |
|------|------|
| 格式 | 结构化 JSON（一行一条） |
| 库 | `go.uber.org/zap` (Production Encoder) |
| 输出 | stdout + 可选文件（`logs/orchestrator.log`） |
| 级别 | Debug / Info / Warn / Error（配置文件控制，默认 Info） |
| 轮转 | 按大小 **100MB** + 保留 **5** 个旧文件 + 保留 **30 天** |
| 轮转库 | `gopkg.in/natefinished/lumberjack.v2` |
| 压缩 | 旧文件 gzip 压缩 |

**每条日志包含字段**：

```json
{
  "ts": "2026-03-27T10:30:00.123Z",
  "level": "info",
  "caller": "handlers/app.go:42",
  "msg": "应用上传完成",
  "app_id": "uuid-xxx",
  "app_name": "MyGame",
  "file_size": 524288000,
  "duration_ms": 12340,
  "request_id": "req-abc123"
}
```

**关键日志事件（必须记录）**：

| 级别 | 事件 | 附加字段 |
|------|------|---------|
| Info | ⓪ 启动 | version, config_path, bind_address |
| Info | ⓪ 关闭 | reason (signal/error), uptime |
| Info | 组件启动 | component, pid, exe_path |
| Warn | 组件崩溃 | component, pid, exit_code, stderr_tail |
| Info | 组件停止 | component, pid, reason (user/crash/shutdown) |
| Info | 应用上传 | app_id, app_name, file_size, format |
| Info | 应用解压完成 | app_id, extracted_size, file_count, duration_ms |
| Warn | 解压失败 | app_id, error, bytes_extracted |
| Info | Sunshine 注册 | app_id, sunshine_app_name |
| Warn | Sunshine 注册失败 | app_id, error, http_status |
| Info | UE5 进程启动 | app_id, pid, exe_path, args |
| Warn | UE5 进程崩溃 | app_id, pid, exit_code |
| Info | UE5 进程停止 | app_id, pid, reason |
| Warn | 健康检查失败 | component, url, error, consecutive_failures |
| Error | 内部错误 | error, stack_trace |
| Warn | 磁盘空间低 | free_bytes, threshold_bytes |
| Info | 配置变更 | changed_fields (脱敏) |

**脱敏规则**：
- `password` → `****`（完全遮蔽）
- `password` → `****`
- Sunshine `username` → 不脱敏
- 请求头中的 `Authorization` → `Bearer ****`

#### 17.1.2 组件日志（Component Log）

**用途**：捕获 ① Sunshine 和 ② web-server 的标准输出/错误输出。

| 属性 | 规格 |
|------|------|
| 来源 | 子进程 stdout + stderr（合并，stderr 标记 `[STDERR]` 前缀） |
| 内存缓冲 | 每组件 **环形缓冲区 2000 行**（最新的 2000 行） |
| 文件落盘 | 可选，`logs/sunshine.log`、`logs/web-server.log` |
| 轮转 | 同 ⓪ 应用日志（100MB / 5 文件 / 30 天） |
| 实时推送 | 通过 WebSocket `component_log` 事件推送给前端 |

**缓冲区设计**：
```go
type RingBuffer struct {
    lines    [2000]string
    head     int
    count    int
    mu       sync.RWMutex
}
```

- `GetLast(n int) []string`：返回最近 n 行
- `Subscribe() <-chan string`：订阅新行（用于 WebSocket 推送）
- 缓冲区满时覆盖最旧的行

#### 17.1.3 操作日志（Operation Log / Audit Log）

**用途**：记录所有用户操作和系统自动操作，用于审计和问题追溯。

| 属性 | 规格 |
|------|------|
| 存储 | SQLite `operation_logs` 表 |
| 保留策略 | **30 天** 或 **10 万条**（先到为准） |
| 清理时机 | ⓪ 启动时 + 每天 03:00（可配置） |
| 查询 | API 支持分页 + 按 target_type / target_id / operation / 时间范围过滤 |

**完整 Schema**：

```sql
CREATE TABLE operation_logs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    target_type TEXT    NOT NULL,  -- 'component' | 'app' | 'system'
    target_id   TEXT,              -- 组件名 或 app UUID（system 级为 NULL）
    operation   TEXT    NOT NULL,  -- 'start' | 'stop' | 'restart' | 'crash' | 'upload' | ...
    result      TEXT    NOT NULL,  -- 'success' | 'failure'
    message     TEXT,              -- 人类可读描述
    detail      TEXT,              -- JSON 格式扩展字段（如 exit_code, file_size, error_stack）
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_logs_target    ON operation_logs(target_type, target_id);
CREATE INDEX idx_logs_operation ON operation_logs(operation);
CREATE INDEX idx_logs_time      ON operation_logs(created_at);
```

**`detail` 字段示例**：

```json
// 上传操作
{"file_size": 524288000, "format": "zip", "duration_ms": 12340}

// 崩溃事件
{"exit_code": -1073741819, "pid": 4567, "stderr_tail": "Access violation..."}

// 注册操作
{"sunshine_url": "https://localhost:47990", "http_status": 200}
```

#### 17.1.4 UE5 应用日志（App Output Log）

**用途**：捕获每个 UE5 应用进程的 stdout/stderr 输出。

| 属性 | 规格 |
|------|------|
| 存储位置 | `apps/{app_id}/output.log`（Sunshine 注册时指定） |
| 轮转 | 不轮转（UE5 进程自身管理日志大小），但 ⓪ 每次启动前**截断**为空 |
| 内存缓冲 | 每应用 **环形缓冲区 500 行**（仅运行中的应用） |
| API 查询 | `GET /api/v1/apps/{id}/logs?lines=200` 返回文件尾部 + 内存缓冲 |
| 实时推送 | 通过 WebSocket `app_log` 事件推送 |

**注意**：UE5 的 `-log` 参数会额外生成 `Saved/Logs/` 目录下的日志，⓪ 不管理这些，仅管理 stdout 重定向的 `output.log`。

#### 17.1.5 请求日志（Access Log）

**用途**：记录所有 HTTP API 请求，用于调试和性能分析。

| 属性 | 规格 |
|------|------|
| 格式 | Gin/Echo 默认中间件格式或自定义 JSON |
| 输出 | 合并到 ⓪ 应用日志（Info 级别） |
| 记录字段 | method, path, status, latency_ms, client_ip, request_id |
| 过滤 | 健康检查路径（`/api/v1/health`）默认不记录（减少噪音），可配置开启 |

**每条请求日志示例**：

```json
{
  "ts": "2026-03-27T10:30:00.456Z",
  "level": "info",
  "msg": "HTTP request",
  "method": "POST",
  "path": "/api/v1/apps/upload",
  "status": 200,
  "latency_ms": 12340,
  "client_ip": "192.168.1.100",
  "request_id": "req-abc123",
  "content_length": 524288000
}
```

#### 17.1.6 Request ID 追踪

- 每个 HTTP 请求分配唯一 `request_id`（UUID v4 短格式，如 `req-abc123`）
- 贯穿请求全生命周期：API handler → 业务逻辑 → Sunshine API 调用 → DB 操作
- 响应头返回 `X-Request-ID`
- WebSocket 推送事件中也包含触发操作的 `request_id`
- 方便从前端错误 → 后端日志 → 组件日志的完整链路追踪

### 17.2 配置管理

#### 17.2.1 配置校验

⓪ 启动时对配置文件进行完整校验：

| 校验项 | 规则 |
|--------|------|
| `bind_address` | 合法的 `host:port` 格式 |
| `username` | 非空 |
| `password` | 非空 |
| `components.*.exe_path` | 文件存在（warn 级别，不阻止启动） |
| `sunshine_api.base_url` | 合法 URL |
| `storage.apps_dir` | 目录可写 |
| `storage.max_upload_size_bytes` | > 0 |
| `process.monitor_interval_seconds` | > 0 |
| `templates.*` | 值为非空字符串 |

校验失败输出所有错误（不仅第一个），然后退出。

#### 17.2.2 配置热更新

- v1.0 不支持热更新：修改 config.json 后需重启 ⓪
- `PUT /api/config` 仅更新运行时可变的配置子集（如日志级别、模板），不含组件路径等结构性配置
- 结构性配置变更需重启

#### 17.2.3 相对路径解析

- 配置文件中的所有相对路径统一解析为**相对于 config.json 所在目录**
- 如 config.json 在 `D:\stream-kit\config.json`，则 `./apps` 解析为 `D:\stream-kit\apps`
- 启动时将所有相对路径转为绝对路径存入内存，后续使用绝对路径

#### 17.2.4 环境变量覆盖

配置字段可通过环境变量覆盖，命名规则：

```
ORCH_SERVER_BIND_ADDRESS=0.0.0.0:9000
ORCH_SERVER_API_KEY=sk-xxx
ORCH_SUNSHINE_API_BASE_URL=https://localhost:47990
ORCH_SUNSHINE_API_USERNAME=admin
ORCH_STORAGE_APPS_DIR=./apps
ORCH_PROCESS_MONITOR_INTERVAL_SECONDS=5
```

前缀 `ORCH_`，层级用 `_` 分隔，全大写。

#### 17.2.5 首次运行

- config.json 不存在时自动生成 `config.example.json` 的副本
- 默认用户名密码 admin/admin，启动时 WARN 提示修改
- 控制台输出：`首次运行，已生成默认配置：D:\stream-kit\config.json，请检查后重新启动`
- 首次运行后退出（不直接启动服务），确保用户检查配置

### 17.6 Windows Defender 建议

部署文档（非代码）中提示用户：
- 将托管目录（`apps/`）加入 Windows Defender 排除列表
- 大量 exe/dll 的实时扫描可能导致解压速度降低 10 倍以上
- Sunshine 本身也建议排除

### 17.7 Sunshine 版本兼容

- 明确支持 Sunshine **v2024.x - v2026.x**（基于 confighttp API 稳定性）
- ⓪ 启动时通过 `GET /api/configLocale` 检测 Sunshine 可达性
- API 不兼容时记录完整响应到错误日志，标记失败

### 17.8 事件通知（Webhook）

当关键事件发生时，⓪ 向配置的 Webhook URL 发送 HTTP POST 通知：

```json
{
  "notifications": {
    "webhook_url": "",
    "events": ["component_error", "component_crashed", "app_crashed", "disk_low"]
  }
}
```

- `webhook_url` 为空则不发送（默认禁用）
- POST body 格式与 WebSocket 事件格式相同
- 发送失败仅记录 warn 日志，不重试（避免级联故障）
- v1.0 只支持 Webhook，不做邮件/Slack 等渠道

### 17.9 Windows Service 部署

⓪ 本身是普通 exe，通过 [NSSM](https://nssm.cc/) 或 [WinSW](https://github.com/winsw/winsw) 注册为 Windows 服务：

```powershell
# NSSM 方式
nssm install StreamKit "D:\stream-kit\orchestrator.exe"
nssm set StreamKit AppDirectory "D:\stream-kit"
nssm set StreamKit DisplayName "Stream-Kit Orchestrator"
nssm set StreamKit Start SERVICE_AUTO_START
nssm start StreamKit
```

**注意事项**：
- **不能**以 SYSTEM 账户运行：Windows Service 运行在 Session 0，与用户桌面（Session 1+）隔离，Sunshine 无法访问 GPU 和显示器
- "允许服务与桌面交互" 选项自 Vista 起已失效，**不要勾选**
- **正确做法**：
  1. 配置 Windows **自动登录**目标用户
  2. NSSM 中设置 "Log on" 为该用户账户（非 SYSTEM）
  3. 或更简单：将 `orchestrator.exe` 的快捷方式放入用户启动文件夹（`shell:startup`）

### 17.10 功能降级矩阵

| 故障组件 | 仍可用的功能 | 不可用的功能 |
|---------|------------|------------|
| ① Sunshine 宕机 | 上传/解压/管理应用、⓪ Web UI、② 管理 | Sunshine 注册（标记 `register_failed`，后续自动重试）、串流 |
| ② web-server 宕机 | 全部管理功能、应用启停 | 浏览器串流 |
| 磁盘满 | 查看状态、启停已有应用、串流 | 上传新应用、日志写入 |
| SQLite 损坏 | 无（⓪ 启动失败） | 全部（需要手动恢复 DB） |

当 ① 不可达时，Sunshine 注册失败的应用进入 `register_failed` 状态。⓪ 在 ① 健康检查恢复后，**自动重试**所有 `register_failed` 状态的应用注册（每次健康恢复时触发一次）。

## 18. API 工程规范

### 18.1 API 版本策略

- 所有 API 路径加版本前缀：`/api/v1/...`
- 当前版本：`v1`
- 不兼容变更发布 `v2`，旧版本保持 6 个月
- 前端静态文件路由不受版本前缀影响（`/` 直接返回 index.html）

### 18.2 错误码目录

| 错误码 | HTTP 状态码 | 说明 |
|--------|-----------|------|
| `APP_NOT_FOUND` | 404 | 应用不存在 |
| `APP_ALREADY_EXISTS` | 409 | 同名应用已存在 |
| `APP_OPERATION_CONFLICT` | 409 | 应用正在执行其他操作 |
| `APP_STATE_INVALID` | 400 | 当前状态不允许此操作 |
| `APP_PROCESS_RUNNING` | 409 | 进程正在运行，需先停止 |
| `COMPONENT_NOT_FOUND` | 404 | 组件名不存在 |
| `COMPONENT_OPERATION_CONFLICT` | 409 | 组件正在执行其他操作 |
| `UPLOAD_TOO_LARGE` | 413 | 文件超过大小限制 |
| `UPLOAD_INVALID_FORMAT` | 400 | 不支持的压缩格式 |
| `EXTRACT_PATH_TRAVERSAL` | 400 | 检测到路径穿越 |
| `EXTRACT_TOO_LARGE` | 400 | 解压后超过大小限制 |
| `EXTRACT_DISK_FULL` | 507 | 磁盘空间不足 |
| `SUNSHINE_UNREACHABLE` | 502 | 无法连接 Sunshine API |
| `SUNSHINE_AUTH_FAILED` | 502 | Sunshine 认证失败 |
| `SUNSHINE_NAME_CONFLICT` | 409 | Sunshine 中已有同名应用 |
| `CONFIG_INVALID` | 400 | 配置格式/值不合法 |
| `UNAUTHORIZED` | 401 | 未登录、JWT 无效或已过期 |
| `INTERNAL_ERROR` | 500 | 服务器内部错误 |
| `OPTIMISTIC_LOCK_CONFLICT` | 409 | 数据已被其他请求修改 |

### 18.3 WebSocket 重连策略

前端 WebSocket 连接断开后的重连逻辑：

```
断开 → 等待 1s → 重连
失败 → 等待 2s → 重连
失败 → 等待 4s → 重连
...
最大间隔 30s，无限重试
重连成功后重置间隔
```

- 每 30 秒发送 ping 帧保活
- ⓪ 60 秒未收到 pong 则断开连接
- 前端重连后⓪ 发送当前全量状态快照（补偿断线期间丢失的事件）

### 18.4 错误响应格式

所有错误响应包含 `request_id` 以便追踪：

```json
{
  "status": "error",
  "code": "APP_NOT_FOUND",
  "message": "应用不存在",
  "request_id": "req-abc123"
}
```

`INTERNAL_ERROR` (500) 响应的 `message` 固定为 "服务器内部错误"，不暴露堆栈信息。
