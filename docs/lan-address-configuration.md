# 局域网地址、HTTPS 与 IP 变更

本文同时覆盖管理端和媒体数据面。只有 IP 的局域网可以部署，不要求购买域名；IP 地址、名称解析、证书信任和媒体可达性需要分别配置。现场地址见[部署基线](release-status.md)，不要把文档中的示例当作实际主机地址。

## 本机、LAN 与协议

| 入口 | 应使用的地址 |
| --- | --- |
| 新安装、本机默认 | `http://127.0.0.1:9000` |
| 已启用 HTTPS、本机 | `https://127.0.0.1:9000/login`，证书须覆盖 loopback |
| 其他设备 | 可达的服务器 LAN IP 或可解析主机名，使用部署实际 scheme/port |
| 观看 | 应用详情的 `/watch#key=…` 永久入口，不是裸 `stream.html?hostId=…&appId=…` |

`127.0.0.1` 总是当前设备自身，不能交给其他电脑/手机访问服务器。已启用 HTTPS 的监听不继续服务 HTTP。远端浏览器录音须可信 HTTPS 和用户授权；localhost 的浏览器安全上下文特例不适用于普通 LAN IP。

## 两类地址分开

内部组件 API 保持本机 loopback，避免绑定 DHCP 地址。对浏览器公开的 URL 由管理页的实际 hostname 和网关端口派生；同机部署通常保持 `moonlight_web.public_url` 为空。

网关生成 `config.js` 时，将内部 loopback/unspecified 控制主机替换为客户端请求的 authority/Host，保留控制端 scheme/port/path；显式外部主机 override 不会被覆盖。CORS `https://{host}:8080` 只匹配当前管理主机、指定协议及端口，不是任意来源白名单。具体规则见[公开地址契约](../contracts/public-addresses.md)。

页面地址正确不能证明数据面正确。还需核对网关信令、ICE/NAT 映射、实际 UDP 范围、防火墙和返回候选，不能向远端返回无法使用的 loopback。

直连的受管会话通过实际接受信令连接的 IPv4 地址绑定媒体 UDP，从而使用当前可达网卡。客户端经另一个接口或新 DHCP 地址重连时，新连接重新读取该地址。显式 NAT 映射、回环反向代理、非 IPv4 信令及独立网关模式沿用其既有 ICE 发现或映射策略。网关仍使用配置的 UDP 端口范围。

## 保持部署 CA 的 TLS 身份维护

启用 `server.lan_tls` 后，控制服务使用**已有部署 CA**维护服务证书。`auto_detect` 默认开启：启动时及运行中每 15 秒核对活动网卡的私有 IPv4/IPv6 地址，合并管理员配置的固定身份；CA 和服务私钥保持不变。管理端使用内存中的有效证书处理新握手，网关每 5 秒检查共用证书并热加载。正常地址变化约 20 秒内覆盖两个入口，无需重启服务或重装客户端信任。

自动识别排除停用、回环、点对点网卡及公网、链路本地、组播地址；自动识别开启时，本机 localhost / 127.0.0.1 / ::1 始终保留。需要隔离 VPN 或多网卡时，用 `auto_interfaces` 指定实际网卡名称。自动地址只存在于当前证书身份，不持续写回配置，也不累积历次 DHCP 地址。暂时没有局域网地址时仍提供本机入口，网卡就绪后自动补充。关闭自动识别后仅采用配置的 `hosts`，需显式保留实际使用的本机身份。

以下是需替换为实际部署值的配置示例：

```json
{
  "tls_cert": "tls/server.crt",
  "tls_key": "tls/server.key",
  "lan_tls": {
    "ca_cert": "tls/ca.crt",
    "ca_key": "tls/ca.key",
    "hosts": [],
    "watch_hostname": "render.local",
    "auto_detect": true,
    "auto_interfaces": []
  }
}
```

这些是 `server` 对象中的字段。相对路径以控制端配置目录解析；四个文件路径必须不同。CA 与服务私钥保持受保护，不随安装器/APK或普通配置导出分发。

管理端与本机网关共用同一服务证书/私钥路径。地址未变且服务证书有效期超过 30 天时不重复签发，临近过期在维护循环续签；CA 失效不能通过静默换根处理。证书读写或网卡枚举失败时保留最后有效身份并记录异常，不关闭当前监听器或改用不安全连接。`check-config` 仅检查，不写入证书，也不代表客户端已信任。

使用 Schannel 的 Windows 命令行客户端如果强制检查证书吊销状态，而部署证书没有提供可查询的吊销信息，可能返回 `0x80092012`。验收 Web 入口时，用已信任部署 CA 的浏览器分别检查管理页和媒体网关。运行环境若要求 Schannel 客户端完成在线吊销检查，应使用带可达吊销信息的组织证书。[Windows 证书错误码](https://learn.microsoft.com/en-us/windows/win32/seccrypto/certificate-and-trust-return-values)

初次由 HTTP 改为 HTTPS 时，必须一并更新管理监听 TLS、网关 TLS、控制/网关内部调用 URL、网关健康检查、CORS、公开 URL 与客户端信任。启用托管部署 CA 后，控制服务对配置为本机 HTTPS 回环地址的媒体网关直接验证该 CA。网关状态同步、管理请求及同源健康检查共用这份信任，无需额外向 Windows 或 Linux 服务账户安装根证书。远程网关、自管证书及其他来源继续按系统信任验证。

## 服务器换 IP：自动恢复和手动覆盖

已有 CA 且启用自动识别的同机 LAN 部署，无需手动登记每个 DHCP 地址。保持通配监听、空 `public_url`、同主机 CORS 模板及内部 loopback，证书和新生成的观看入口随当前访问地址更新。网络切换本身可能中断已有连接，证书热更新不主动断开连接；客户端须通过可达地址重新连接，不能把旧 IP 变成新 IP 的网络路由。

公网 NAT、显式外部 URL、自管证书，或者关闭自动识别的部署，仍按下面流程维护。自动检测不修改防火墙、网卡、手动监听地址或 NAT 映射。

1. 在本机可信入口或管理员终端确认真实新 IP、当前监听、组件及应用状态。不要猜空闲 IP、改网卡别名或结束其他项目进程。
2. 通过后台正常停止活动应用，等待原生实例和会话终态；备份受保护配置及原证书，准备回退。
3. 在服务配置的“局域网 TLS 身份维护”核对自动识别开关及网卡名称；手动覆盖身份写入 `server.lan_tls.hosts`，保留实际使用的固定主机名。
4. 核对具体 bind 地址、显式公开 URL、CORS literal、ICE/NAT 映射及防火墙接口。通配 bind、空 public_url、同主机模板及内部 loopback 无需为了换 IP 改成具体地址；远端节点只更新确实迁移的节点。
5. 执行原生控制端及网关配置预检。保存期望值并不使当前监听自动重载。
6. 配置策略变更需只重启 Stream Kit；之后普通网卡地址变化由运行时自动处理。原 CA 和原服务私钥下生成新证书，两个入口采用一致身份。核对控制端及自动组件就绪。
7. 在已信任客户端用新地址打开管理页，再打开同一应用的永久入口。检查实际视频、程序音、目标输入、麦克风到录音端点及观看端；TLS、页面与数据面分别确认。
8. 成功后保持应用/密钥，按需恢复运行；失败先停归属服务并恢复备份配置/证书，不叠加忽略 TLS 或新 CA 的绕过。

Windows 受保护配置和 SCM 重启需要管理员权限/UAC；这不是重新安装。恢复旧配置只能恢复旧地址身份，网络若已改变仍需按真实地址维护，不能承诺旧 IP 一定可达。

## 书签和 Android 地址

在「系统设置 → 管理服务 → 局域网 TLS 身份维护」填写「固定观看主机名」，例如本机已有 mDNS 公布的 `render.local` 或局域网 DNS 可解析的主机名。服务使用通配监听和固定 HTTPS 端口。保存后重启管理服务，原部署 CA 会为固定主机名签发证书。管理页用数字 IP 打开时，应用详情复制的观看链接也使用已配置的固定主机名。此设置保留应用密钥，无需重置观看链接。

已保存的数字 IP 书签需更新一次地址部分，保留同一 key。改用固定主机名后，在客户端仍能解析并访问该主机名的网络内，之后的 DHCP 换址无需改书签、重装证书或重编 APK。`.local` 使用同一网络链路上的 mDNS。跨 VLAN 或禁止组播的网络需要管理员能控制的 DNS 和有效路由。

Android 可直接导入固定主机名链接，也可在入口「修改服务器地址」把已保存的数字 IP 更新为固定主机名和 HTTPS 端口，保留观看密钥。原部署 CA 未更换时沿用原信任。仅客户端自己换 IP 时，重新连接后权限仍由管理端分配。

使用稳定主机名可减少改书签，但依赖 LAN DNS/mDNS 和客户端解析。复用 Sunshine 的 Windows `DnsServiceRegister` 或 Linux Avahi 发布 `电脑名.local`，不要再加发现守护进程。访客 Wi-Fi、跨 VLAN、组播隔离及某些设备解析支持会影响可达，需实际验证；证书必须覆盖同一主机名。

多网卡部署应从独立客户端核对固定主机名解析出的地址和浏览器实际连接的地址，再检查媒体连接选中的网络路径。本机能打开同一主机名只证明本机可达。若局域网客户端解析到不可达的虚拟网卡或 VPN 地址，应核对实际 DNS/mDNS 发布与路由。调整证书的网卡筛选只改变自动纳入证书的 IP。

## 证据与维护边界

自动热更新的[隔离 Linux 实验](evidence/lan-autodiscovery-515b9918-20261119.json)实际移除旧地址并增加新地址，6.93 秒后两个 HTTPS 监听均通过新数字 IP 的原 CA 校验，旧 SAN 移除；控制端、网关及渲染端 PID、配置和私钥保持，浏览器无需重载即恢复到新媒体地址。该记录保留其真实运行源码，不代表共享 Windows 主机或 Android 真机已执行同样的网络切换。

本机新 IP 入口状态及既有独立网络实验见[部署基线](release-status.md)。已有服务器 Running/Auto、原生预检、页面 200、组件重启、整机重启和完整媒体恢复分别证明，不可相互替代。

共享宿主机的网卡切换或整机重启会影响其他开发及远程连接，须在明确维护窗口执行，保护 UE、ToDesk 和已有数据。不能用额外网卡别名冒充真实主地址迁移，不能通过修改系统信任或降低 TLS 校验获取通过结果。
